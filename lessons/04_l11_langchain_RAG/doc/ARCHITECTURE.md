# Архитектура решения

## Компоненты

```
┌─────────────┐    PDF/TXT      ┌───────────────┐   embeddings   ┌──────────┐
│  docs/*.pdf │ ─────────────▶  │ RecursiveChar │ ─────────────▶ │  Qdrant  │
│  docs/*.txt │   (PyPDFLoader) │ TextSplitter  │ (HF MiniLM-L12)│ (docker) │
└──────────v──┘                 └───────────────┘                └────┬─────┘
                                                                      │ similarity_search
                                                                      ▼
                          ┌───────────────────────────────────────────────┐
User question ───────────▶│  LCEL chain: {context, question} -> prompt    │
                          │  -> ChatOllama(llama) -> StrOutputParser      │
                          └───────────────────────────────────────────────┘
                                                                     │
                                                                     ▼
                                                              Gradio UI
```

## Почему такой стек

- **Ollama** — самый простой способ гарантировать полную изоляцию LLM от интернета;
  изначально была выбрана модель `qwen3.5:4b` выбрана как компромисс между скоростью 
  на CPU и качеством ответа на русском/английском (см. таблицу в README.md), но локально 
  она работала не быстро.
- **HuggingFace sentence-transformers (`paraphrase-multilingual-MiniLM-L12-v2`)** —
  компактная (470MB) мультиязычная модель эмбеддингов, работает на CPU за
  доли секунды на чанк, не требует API-ключей.
- **Qdrant** — легковесная векторная БД с нативной поддержкой метаданных
  (имя файла, страница), удобно поднимается в docker-compose, есть
  готовая интеграция `langchain-qdrant`.
- **LangChain LCEL** — та же парадигма Runnable-цепочек, что и в учебном
  ноутбуке (`prompt | model | output_parser`), только вместо
  `RunnableWithMessageHistory` используется retrieval-шаг перед промптом.
- **Gradio** — минимальный чат-интерфейс с историей на 1 чат и слайдером 
  Top-K для экспериментов.

## Параметры чанкования

- `chunk_size=1800`, `chunk_overlap=120` — сбалансированный размер для
  RU/EN технических документов (регламенты, инструкции): достаточно
  контекста на один чанк, но не превышает разумный лимит промпта для
  4B-модели на CPU.`chunk_size=800` - изначально поставленный - не хватало контекста.
- Их можно менять через `.env` (`CHUNK_SIZE`, `CHUNK_OVERLAP`) без правки кода.

## Системный промпт

```
Ты корпоративный ассистент. Отвечай на вопрос пользователя
ТОЛЬКО опираясь на следующий контекст, полученный из внутренних документов компании.
Если ответа в контексте нет — прямо скажи, что не знаешь, и не придумывай факты.

Контекст:
{context}
```

Это прямая реализация требования из TASK_RU.md (п.3.3) — модель обязана
отказываться отвечать вне контекста и не полагаться на собственные знания
при конфликте фактов.

## Ограничения локального развертывания (CPU, без GPU)

- Латency генерации на 4B модели заметно выше, чем у облачных API (десятки и сотни 
  секунд на таймаут  vs доли секунды на токен) — критично при больших Top-K 
  и длинных контекстах.
- Оперативная память: модель 3.4GB + эмбеддинги + Qdrant в docker — суммарно
  комфортно работает от 32GB RAM linux, c хромом и разработкой кроме.
- Возможны более частые галлюцинации на слабых 3-4B моделях при
  плохо сформулированном промпте — важно тестировать разные Top-K (см. tests/).
