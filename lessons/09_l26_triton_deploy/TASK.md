# Домашнее задание
## Оркестрация моделей в Triton Inference Server

## Цель:

В этом ДЗ вам предстоит развернуть сложный ML-пайплайн в NVIDIA Triton и провести его нагрузочное тестирование. Вы научитесь конфигурировать разные бэкенды для моделей и настраивать бизнес-логику на уровне сервера.

## Описание/Пошаговая инструкция выполнения домашнего задания:

### 1. Подготовка моделей и структуры репозитория.

Подготовьте три разнородные легковесные модели для демонстрации работы разных бэкендов:

Модель классификации: Например, крошечный BERT или классификатор на базе Scikit-learn (в формате ONNX).
Модель эмбеддингов: Например, Sentence-Transformer (в формате ONNX или через Python-бэкенд).
Модель генерации: Малая LLM (например, Qwen-0.5B или TinyLlama), оптимизированная через vLLM или TensorRT-LLM.

Спроектируйте и создайте файловую структуру Model Repository строго по стандартам Triton:

Создайте папки для каждой модели с версионированием (папка 1/).
Подготовьте файлы конфигурации config.pbtxt для каждой модели.
Опишите в конфигах входные (input) и выходные (output) тензоры, их типы данных и размерности.
Выберите и настройте бэкенды для каждой модели (например, onnxruntime для классификации и vllm для генерации).

### 2. Разработка бизнес-логики (Business Logic Scripting — BLS).

Создайте отдельную «ансамблевую» модель (на базе Python Backend), которая будет выступать дирижером всей системы.

Напишите Python-скрипт (model.py), реализующий логику BLS:

Прием входного запроса от пользователя.
Последовательный или параллельный вызов других моделей внутри Triton (используя pb_utils.InferenceRequest).
Логика обработки: например, сначала получаем эмбеддинг текста - на основе эмбеддинга вызываем классификатор - если класс «вопрос», отправляем текст в модель генерации.
Сборка финального ответа и возвращение его клиенту.
Настройте config.pbtxt для этой BLS-модели, указав зависимости от других моделей.

### 3. Развертывание в Docker и запуск сервера.

Подготовьте Dockerfile или используйте готовый образ nvcr.io/nvidia/tritonserver.

Настройте запуск контейнера с пробросом нужных портов (8000 для HTTP, 8001 для gRPC, 8002 для метрик) и монтированием папки model_repository.

Запустите сервер и убедитесь через логи (tritonserver --model-repository=/models), что все модели успешно перешли в статус READY.

Напишите простой клиентский скрипт на Python (используя tritonclient), чтобы проверить работоспособность всей цепочки (BLS-пайплайна) через один запрос.

### 4. Нагрузочное тестирование и анализ слабых мест.

Используйте утилиту Perf Analyzer (часть Triton SDK) для проведения нагрузочного тестирования.

Выполните замеры для двух сценариев:

Нагрузка на каждую модель по отдельности.
Нагрузка на всю цепочку через BLS-модель.

Проанализируйте полученные метрики:

Throughput (Пропускная способность): Сколько запросов в секунду (RPS) выдерживает система.
Latency (Задержка): Какое время занимает выполнение запроса на разных этапах (Queue, Compute Input, Compute Infer, Compute Output).

Определите узкие места: какая модель в цепочке вносит наибольшую задержку? Посмотрите на загрузку GPU/CPU через nvidia-smi или метрики Triton на порту 8002.

### 5. Отчёт и анализ.

Соберите результаты в GitHub-репозиторий. Опишите, что настроено, и приведите следующие артефакты:

Иерархическое дерево вашего Model Repository.
Содержимое файлов config.pbtxt и код вашего BLS-скрипта (model.py).
Отчёт о тестировании: Скриншоты или текстовые логи работы Perf Analyzer с итоговыми цифрами Latency и Throughput.
Графики или таблицы со сравнением производительности моделей.
Сделайте вывод: какие преимущества дает использование Triton и BLS по сравнению с обычным Flask/FastAPI сервисом? Предложите способы оптимизации (например, включение Dynamic Batching или Instance Groups), если задержки оказались слишком высокими.
